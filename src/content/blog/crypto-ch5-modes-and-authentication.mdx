A block cipher encrypts 16 bytes. Everything interesting happens in how you chain blocks together, and in whether you can tell if someone changed them.

## The ECB penguin

ECB mode encrypts every block independently with the same key, so identical plaintext blocks give identical ciphertext blocks. The lab encrypts a flat-colour mascot image three ways:

![The original image, then ECB, CBC and CTR encryptions of it](/blog/ecb-vs-cbc-ctr.png)

In the ECB output the penguin's outline is plainly visible: only the colours changed. Counting repeats makes it precise: **4,674 of the 4,800 ciphertext blocks were copies of an earlier block** in ECB, versus **zero** for CBC and CTR. ECB leaks wherever data repeats: images, tables, headers, zero padding.

## Encryption is not integrity

The lab builds AES-GCM from primitives (CTR encryption plus GHASH, a polynomial MAC over GF(2^128)) and checks it against the published test cases. Then it flips one ciphertext bit in two settings:

- **GCM:** the tag check fails and no plaintext is returned.
- **Plain CTR:** it silently decrypts to attacker-chosen text. Guess that byte 11 of "PAY ALICE $100.00" is a 1, XOR the ciphertext byte with the difference between "1" and "9", and the recipient reads $900.00. No key needed.

## Auditing real TLS

The TLS auditor tries every cipher suite the local OpenSSL offers (137) against a server, individually. Pointed at two deployments I own, both came back clean: TLS 1.0 and 1.1 refused, TLS 1.2 and 1.3 accepted, only ECDHE plus AEAD suites, HSTS enabled. The remaining gaps were missing response headers, which the write-up fixes with concrete config. The tool also says when it cannot test something, rather than guessing.

## A tamper-evident encrypted log

The last exercise designs a log encryptor around four decisions:

- AES-256-GCM, with a separate key per log segment derived from a master key.
- The record sequence number as the nonce, which is safe because keys are per segment and there is one writer.
- Each record's associated data includes a hash of the previous record, so deleting, reordering or replaying any record breaks the chain.
- A MAC'd checkpoint stored elsewhere, because nothing inside the file can reveal that the last records were cut off. The test asserts that limitation on purpose.
